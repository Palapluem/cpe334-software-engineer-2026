\qtitle{1}{วิเคราะห์ความต้องการ}{8}
\solsource{Lecture 10 หน้า 5-6; Lecture 2 หน้า 14-26}
\textbf{คำย่อ:} FR (Functional Requirement) บอกหน้าที่; NFR (Non-functional Requirement) บอกระดับคุณภาพ\par
\anshead{1.1 ดู workshop ที่เปิดลงทะเบียน}{2}
เป็น FR เพราะให้นักศึกษาที่เข้าสู่ระบบดู workshop เพื่อเลือกสมัคร; คงข้อความได้หากตกลงคำว่า “เปิดรับ” แล้ว มิฉะนั้นต้องถามเพิ่ม; ทดสอบรายการเปิด/ปิด ต้องเห็นรายการเปิดครบและไม่เห็นรายการปิด

\anshead{1.2 ลงทะเบียนรวดเร็ว}{2}
เป็น NFR ด้าน performance เพราะเน้นความเร็ว แต่ยังวัดไม่ได้; เสนอให้คำขออย่างน้อย 95\% ตอบภายใน 2 วินาทีเมื่อมีผู้ใช้พร้อมกัน 100 คน (รอยืนยัน); ใช้ load test วัดตั้งแต่ส่งคำขอถึงได้ผล ต้องผ่านเกณฑ์นี้

\anshead{1.3 ไม่เกิน 3 workshop ต่อภาค}{2}
เป็น business/domain rule เพราะจำกัดสิทธิ์ตามนโยบาย; คงเกณฑ์ 3 รายการต่อภาค แต่ยืนยันสถานะที่นับ; ทดสอบมี 2 เพิ่มเป็น 3 ต้องผ่าน ส่วนมี 3 ขอรายการที่ 4 ต้องถูกปฏิเสธและจำนวนยังเป็น 3

\anshead{1.4 ยกเลิกและดูรายชื่อ}{2}
เป็น FR แต่ไม่ atomic เพราะรวมสองหน้าที่; แยกเป็นนักศึกษายกเลิกการสมัคร กับผู้ประสานงานดูรายชื่อ; ยืนยันสิทธิ์และเงื่อนไข แล้วทดสอบแต่ละบทบาท ต้องยกเลิกได้ตามสิทธิ์และรายชื่อตรงข้อมูล\par\smallskip
\solextra{ข้อ 1.2 เป็นตัวอย่างค่าที่เสนอ ไม่ใช่ค่าจากโจทย์ ต้องตกลงชุดข้อมูล เครือข่าย จุดวัดและกรณีผิดพลาดก่อนใช้รับงาน; ข้อ 1.3 ต้องถามว่าการยกเลิกนับรวมโควตาหรือไม่}
\textbf{เกณฑ์ตรวจต่อข้อย่อย 2 คะแนน:} ประเภทพร้อมเหตุผล 0.25; จุดประสงค์ 0.25; คุณภาพ 0.50; วิธีตรวจและผลคาดหวัง 0.50; ปรับหรือคงข้อความพร้อมเหตุผล 0.50 ข้อ 1.2 รับ NFR ด้าน usability หากนิยามและวิธีวัดสอดคล้องกัน

\solextra{ข้อมูลยังไม่พอคำนวณ effort จริง จึงไม่กำหนดตัวเลขขึ้นเอง ข้อเสนอเรื่องตัวชี้วัด ความเสี่ยง วิธีประเมินแรงงานและหลักฐานรับงานยังต้องยืนยัน ไม่ใช่ข้อตกลงเดิม}
\textbf{เกณฑ์ตรวจ:} คงปัญหา ผู้ใช้ วิธีแก้ คุณค่าและขอบเขตเดิม 1; เติมความเสี่ยงและแนวประเมิน effort โดยระบุสิ่งที่ยังต้องยืนยัน 1; หลักฐานรับงานตรวจได้ 1 รับประมาณการเชิงตัวเลขที่ระบุสมมติฐานและมีเหตุผลรองรับ แต่ไม่บังคับตัวเลขใด

RBAC (Role-Based Access Control) คือกำหนดสิทธิ์ตามบทบาท; Student = นักศึกษา, Coordinator = ผู้ประสานงาน\par
\begin{tabularx}{\linewidth}{|Y|C{2.8cm}|C{2.8cm}|}\hline

ดู workshop ที่เผยแพร่ & Allow & Allow\\\hline
ส่งคำขอลงทะเบียนของตน & Allow & Deny\\\hline
สร้าง workshop & Deny & Allow\\\hline
แก้ไข workshop & Deny & Allow\\\hline
ส่งออกรายชื่อ & Deny & Allow\\\hline
\end{tabularx}
\textbf{3.2:} ไม่พอ เพราะผู้ใช้เรียก API โดยไม่ผ่านปุ่มได้ server ต้องยืนยันตัวตน (authentication) แล้วตรวจสิทธิ์ (authorization) จากข้อมูลที่เชื่อถือได้ ใช้ default deny: ไม่ได้รับสิทธิ์ต้องปฏิเสธ ไม่เชื่อ role ที่แนบมากับคำขอ\par
\solextra{ตัวอย่างทดสอบที่เสนอ: ใช้บัญชี Student เรียกส่งออกรายชื่อโดยตรง แม้ปลอม role=Coordinator ต้องได้ 403 และไม่ได้รับรายชื่อ; รหัสตอบกลับนี้เป็นแบบที่เสนอ ไม่ใช่ API contract ที่โจทย์ให้}
\textbf{เกณฑ์ตรวจ:} 3.1 ช่องละ 0.25 รวม 2.5; 3.2 แยก UI/การบังคับสิทธิ์ 0.5, ตรวจสิทธิ์ที่เชื่อถือได้และ default deny 0.5, ทดสอบตรงพร้อมผลคาดหวัง 0.5 ไม่เพิ่ม inheritance หรือกฎเจ้าของที่โจทย์ไม่ได้ให้

\qtitle{11}{Switch ทำ commit แยกสาย แล้ว merge}{10}
\solsource{โจทย์สถานการณ์ดัดแปลงในชุดฝึก; หลัก three-way merge และ refs: Samples หน้า 6, 12, 21}
\textbf{ก่อน merge:} C และ D ต่างมี parent เป็น B เพราะทำงานต่อจาก B คนละ branch ไม่ใช่ C ตามด้วย D ในเส้นเดียว HEAD อยู่ sprint\_1\_staging ที่ D หลัง switch ครั้งที่สอง
\begin{gitpanel}
A---B---D [HEAD -> sprint_1_staging]
     \
      C [feature/load_scores]

main, origin/main, origin/sprint_1_staging -> B
origin/feature/load_scores -> B
\end{gitpanel}
\textbf{หลัง merge:} E เป็น merge commit ที่มี first parent D และ second parent C; เลื่อนเฉพาะ sprint\_1\_staging ไป E โดย HEAD ยังชี้ branch เดิม
\begin{gitpanel}
A---B---D---------E [HEAD -> sprint_1_staging]
     \           /
      C---------/

main, origin/main, origin/sprint_1_staging -> B
feature/load_scores -> C
origin/feature/load_scores -> B
\end{gitpanel}

\textbf{เหตุผล:} เป็น three-way merge เพราะ C กับ D แยกจาก common ancestor B ไม่มีปลายใดเป็น ancestor ของอีกปลาย จึง fast-forward ไม่ได้ source branch คงที่ C และ origin/* คงที่ B เพราะไม่มี fetch หรือ push การ switch เปลี่ยน current branch/working tree แต่ไม่สร้าง commit; C และ D เกิดจาก commit สองคำสั่ง ส่วน E เกิดจาก merge\par
\textbf{เกณฑ์ตรวจ 10 คะแนน:} C และ D มี parent B ครบ 2; local branches/HEAD ก่อน merge ถูก 2; E มี parents D และ C ครบ 2; current branch/HEAD หลัง merge ถูก 1; คง main, source branch และ remote refs ถูก 2; อธิบาย three-way และ switch ไม่สร้าง commit 1\par
\textbf{รูปแบบคำตอบ:} รับภาพวงกลมกับเส้นเชื่อมหรือ ASCII ที่สื่อ ancestry เดียวกัน อย่าเติม commit ใหม่เพียงเพราะมี switch และอย่าเลื่อน origin/* ตาม local branch โดยไม่มีการติดต่อ remote

\anshead{12.3 Inspect, stage และ commit}{5}
\begin{gitpanel}
> git status
> git diff -- score_data.py scores.csv
> git add -- score_data.py scores.csv validation_notes.txt
> git diff --cached -- score_data.py scores.csv validation_notes.txt
> git commit -m "Document score validation cases"
\end{gitpanel}
\textbf{เหตุผลสั้น:} \code{status} ดูสถานะไฟล์; \code{diff} ดูส่วนต่างของไฟล์ที่ Git ติดตามแล้ว; \code{diff --cached} ตรวจสิ่งที่เลือกไว้หลัง stage รวมไฟล์ใหม่ ก่อนสร้าง commit รับวิธีอื่นที่ตรวจครบและเลือกเฉพาะสามไฟล์

\begin{gitpanel}
A---B [main, origin/main]
     \
      C---D---E---F [HEAD -> sprint_1_staging]

feature/load_scores -> E
origin/sprint_1_staging -> C
\end{gitpanel}
F มี parent E ตัวเดียวและบันทึกการแก้ทั้งสามไฟล์; sprint\_1\_staging = F โดย HEAD ชี้ branch นี้ ส่วน feature/load\_scores = E, main และ origin/main = B, origin/sprint\_1\_staging = C เพราะไม่มีคำสั่งติดต่อ remote จึงคง remote-tracking refs เดิม

\textbf{เกณฑ์ตรวจ 5 คะแนน:}
\begin{itemize}
\item Inspect เห็นสถานะและเนื้อหาการเปลี่ยนแปลงที่จะ commit รวมไฟล์ใหม่ 1
\item Stage ชื่อไฟล์สามรายการชัดเจน ไม่ใช้ \code{git add .} 1
\item Commit ด้วยข้อความที่กำหนด 1
\item F ต่อจาก E และ local sprint/HEAD ไป F 1
\item pointers อื่นคงครบและไม่สร้าง merge commit แทรก 1
\end{itemize}
หากกราฟผิดสืบเนื่องจาก 12.2 ให้ตรวจขั้นใหม่บน branch และ ancestry ที่ผู้ตอบวาดอย่างสอดคล้อง ให้คะแนนทักษะใหม่ที่ถูกต้อง ไม่หักต้นเหตุเดิมซ้ำทั้งข้อ
